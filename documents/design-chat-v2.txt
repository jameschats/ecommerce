Commerce Platform — V1 → V2 Design
1. What Changes from V1 to V2
V1 is a single-store app — one business, one catalog, one set of customers. V2 transforms it into a platform where many independent merchants each run their own fully isolated store on your infrastructure, like Shopify.
DimensionV1 — Single StoreV2 — Commerce PlatformWho sells?You (one seller)Many merchants, each independentCustomers belong toYour platformEach merchant's storeProducts belong toYour catalogEach merchant's own catalogStorefrontOne Angular appOne storefront per merchant (subdomain)PaymentsYour Razorpay accountEach merchant's own Razorpay accountYour revenueProduct salesMonthly subscription fees from merchantsAdmin panelManages your storeSuper-admin + per-merchant adminThemesOne global themeEach merchant sets their own brandingEmail / SMSYour brand nameSent under each merchant's brand
The single most important engineering principle: every database query must be scoped to a TenantId. One data leak between tenants is a catastrophic trust failure. EF Core's Global Query Filter pattern enforces this automatically so no developer has to remember to add it manually.

5. The 7 Major Engineering Changes
5.1 Multi-Tenant Data Isolation
Every EF Core entity with a TenantId gets a Global Query Filter. Every LINQ query automatically adds WHERE TenantId = @currentTenant without any developer remembering to do it manually.
csharp// In EcommerceDbContext.OnModelCreating:
modelBuilder.Entity<Product>()
    .HasQueryFilter(p => p.TenantId == _tenantContext.CurrentTenantId);

// CurrentTenantService resolves tenant from the HTTP request:
public class CurrentTenantService : ICurrentTenantService {
    public Guid CurrentTenantId => _httpContext.Items["TenantId"] as Guid?
                                   ?? throw new UnauthorizedAccessException();
}

⚠️ Any raw SQL (Dapper, ADO.NET) must manually add AND TenantId = @tenantId. Every raw SQL call in the codebase must be audited and tagged as // TENANT-SCOPED.

5.2 Tenant Resolution Middleware
Every incoming HTTP request resolves the tenant from the subdomain before any controller runs.
csharpvar host = context.Request.Host.Host;  // sarahs-boutique.yourplatform.com
var slug = host.Split('.')[0];          // sarahs-boutique
var tenant = await _tenantRepo.GetBySlugAsync(slug);
if (tenant == null || !tenant.IsActive) { context.Response.StatusCode = 404; return; }
context.Items["TenantId"] = tenant.TenantId;

5.7 Per-Tenant Branding, Email & Notifications

Theme Engine (already built in V1) — colors, logo, font stored per TenantId instead of globally.
Transactional emails sent as "Your order from Sarah's Boutique" — TenantSettings.SenderName per tenant.
Notification templates stored per tenant; merchants can customise order confirmation, shipping updates, etc.

8. V2 Build Stages
V2-0 — Tenant Infrastructure (gate: integration tests must prove cross-tenant isolation before any other stage starts)
Activate Tenants table, TenantResolutionMiddleware, CurrentTenantService, HasQueryFilter on all entities, cross-tenant isolation tests.
V2-1 — Plans & Merchant Onboarding
Plans table seeded (Starter/Growth/Pro), merchant signup flow, auto-subdomain provisioning, Razorpay Subscriptions integration, trial-to-paid conversion, billing webhook handler.
V2-2 — Merchant Admin Portal
New Angular app, merchant JWT carries TenantId claim, all V1 admin screens ported, merchant billing portal.
V2-3 — Super Admin Panel
Separate Angular app, unfiltered queries with explicit TenantId scope, tenant management, impersonation, platform revenue dashboard.
V2-4 — Per-Tenant Storefront
Angular shell reads subdomain on bootstrap, calls /api/tenant/resolve, per-tenant SEO meta and theme.
V2-5 — Per-Merchant Payments
Razorpay Route setup, merchant OAuth connection flow, platform commission deducted at source.
V2-6 — Hardening
Plan limit enforcement, Redis with tenant-namespaced keys, per-tenant rate limiting, load testing with 50 simulated tenants, tenant data export.
